# Seat: Perplexity (pasted 2026-09-01)

## 1. Depth
Countersign currently looks like pre-scripted fraud theater: the fake CEO loses because the seed says Frankfurt, no push response, unknown beneficiary, wrong Hartwell facts. The conversation decorates the decision; it does not yet materially determine it. The APort paper's result is that an independently enforced, fail-closed authorization layer can prevent tool execution even when a model is socially engineered (0 breaches in 879 attempts at its top tier, limited to its testbed). Countersign must demonstrate the voice-specific increment over that pattern.

Live-only evidence (must alter the policy result, not just animate the UI): first-stated request terms (commit the initial structured claim as immutable evidence; every later change becomes a typed delta); cross-turn contradiction (generate contradiction checks for ANY field the caller supplied; display field path, timestamp, source quote, change type); adaptive knowledge challenge (challenge graph of at least 12 facts, chosen conditioned on claims and already-used facts, no reuse); clarification quality (deterministic response schema per challenge: exact match, alias match, partial-but-consistent, refusal, contradiction, unsupported assertion); conversation-derived request context (compare caller-extracted beneficiary, amount, currency, timing, change type, justification against the known-payment record server-side); turn behavior (operational-risk evidence only: "caller prevented completion of checks 4 times," never "sounds fraudulent"); disclosure response (offer structured alternatives: callback, app approval, supervisor route, scheduled approval; record acceptance/rejection); recovery after misunderstanding (caller-correction events preserving raw transcript and corrected field, mandatory confirmation before policy use).

The decision must have counterfactual movement. Build a counterfactual panel after each call: what evidence caused this result; what single change would have changed it; what remained unresolved; which claims came from the caller vs simulated systems; would this stage if consistent; would a $45,000 vendor amendment be handled differently. Do not make every rail fail for the CEO. Four live variants: legitimate Dana amendment → STAGE; CEO impostor with wrong secrets → FREEZE; CEO impostor with correct cheat-sheet facts, calm → ESCALATE or FREEZE by policy, not "voice fraud detected"; real Dana with a confusing but valid emergency, initially inconsistent then explains → ESCALATE, not automatic FREEZE. The fourth row is crucial: without a false-positive demonstration the product reads like a machine that punishes stress and imperfect memory.

Ranking: 1 story ledger (essential; must handle corrections, ambiguity, number normalization, STT uncertainty); 2 adaptive challenge selection (essential; fixed Hartwell questions are memorization bait); 3 replayable adversarial corpus (essential for credibility; 20–30 is too thin unless categorized and mutation-tested); 4 timing signals (useful but dangerous: must never appear to infer fraud from hesitation, disability, language, accent, stress); 5 stalling library (production polish, weak differentiation; do not oversell stalling as security); 6 eight hold-the-floor lines (cosmetic unless instrumented; the metric is whether verification finishes before the user abandons).

Missing mechanics: 1 challenge entropy and one-time facts (per-session randomized selection from a larger private fact graph; if every judge can read Calder & Finch from the cheat sheet, that is an open-book test); 2 claim provenance on every card (caller said it / caller corrected it / simulated system returned it / policy-derived / unknown-unresolved); 3 transcript-confidence gating (explicit readback for high-risk fields: "I heard one point eight million dollars. Is that correct?"; do not evaluate the amount until confirmed); 4 ambiguity budget (types UNKNOWN, APPROXIMATE, CORRECTED, CONTRADICTED, CONFIRMED); 5 independently signed simulated-system attestations (a hash chain from one process is decorative; sign each mock response with a distinct demo key); 6 mutation testing for policy (ship deliberate mutants, show tests fail); 7 negative tests against the policy (calls where the LLM is socially engineered into wanting to stage, while the server monitor blocks); 8 a one-click hostile mode (randomized fact packs, hidden scenario configs, exported decision trace).

"Could not have scripted that": hidden challenge-graph selection plus a post-call counterfactual proof. Six hidden scenario seeds (different vendor facts, approval chains, histories, device states); the caller improvises; the engine picks the next question from what was claimed, locks each claim with verbatim evidence, and presents a post-call trace ("You claimed beneficiary A at 00:16, then B at 00:51. The system selected challenge CH-17 because you claimed prior vendor familiarity. If you had retained A and accepted an authenticated callback, the outcome would have been ESCALATE, not FREEZE.").

## 2. Positioning
Likely top 10–20% on presentation and seriousness, not a reliable top-five entry. Signature failure mode of enterprise-security hackathon entries: a polished mock workflow that promises a product category without proving a sharp, generalizable technical insight. lablab listing shows 1,390 participants at present.

By criterion: Presentation, top 10% if it works / top 40% if it stutters; weakest = part 8 density; change = a "judge path" with one giant changing claim, one active check, one consequence. Business value, top 25%; weakest = no buyer, deployment model, procurement path, or false-positive economics; change = narrow to treasury exception desk / bank call-center escalation overlay with one quantified workflow. Application, top 15% if live adaptation exists / top 35% if seeded; weakest = browser-side policy and LLM-mediated extraction; change = server is the sole authorization authority; exploit live API configuration to change only safe conversational behavior by state. Originality, top 20%; weakest = deterministic policy before action is established prior art and cloned-voice fraud is crowded; change = the original contribution is a reusable, tested "spoken-evidence policy runtime," not another deepfake detector story. Participant vote: likely below visual consumer apps; the consumer coda looks bolted on; delete it or make it a separate coherent demo.

Under-used AAI features: live configuration updates (in CHALLENGE, update turn-taking to permit longer pauses; in CONTAINMENT, short neutral prompts and remove all sensitive tools; show the config-change event); server-side HTTP tools (use for all evidence acquisition and all authority-bearing actions; the browser must never invent a tool result); client-side function tools (purely presentational); session resumption (resume the conversation but mark every pending high-risk request as needing fresh verification after reconnect); phone/SIP (a real phone number as a secondary demo); DTMF PCI mode (contrast slide: payment credentials never enter the transcript); keyterms (before/after transcript test for Meridian Supply, Calder & Finch, dollar figures, account suffixes); observability (compact event audit). ## 3. Improvisation
30 moves with required states, including: OPENING_TIMEOUT; MIC_UNAVAILABLE preflight; UNINTELLIGIBLE counter (never create claim facts); unsupported language disclosure; explicit confirmation for critical fields under accent/slow speech; AMENDMENT_REQUEST (legitimate amendment vs unknown payment creation); OOB_DECLINED; UNRECOGNIZED_ROLE (Marcus); "I'm testing" after a CEO claim must NOT erase prior claim history (exploitable as written); TRANSPARENCY_QUERY (no policy thresholds, challenge inventory, or simulated-system details); ANTI_COACHING; wrong cheat-sheet reading → treat the actual utterance as evidence; correct cheat-sheet facts → hidden/random challenge selection, correct answer never alone establishes authority; REFUSAL_LIMIT; interruption storms → containment script; HUMAN_REQUEST → verified callback or supervisor queue; "release it anyway, I accept all risk" → absolute invariant; prompt injection → tool gateway rejects, record PROMPT_INJECTION_ATTEMPT as content not proof; CALL_ENDED_PENDING (expire request, no action); RECONNECT_PENDING (resume context, invalidate terminal authorization, rerun checks); IDENTITY_SWITCH (preserve both, reset assurance to zero); new beneficiary below $50k → separate risk class, never voice-stage without prior vendor verification; splitting $84,500 into two $42,250 → aggregate exposure rule (catastrophic as written); similar-sounding account suffix → digit-confirmed readback, ambiguity → ESCALATE; DELEGATION_CLAIM (only pre-registered delegation); PRIVACY_QUERY; accessibility/text fallback (never frame inability as suspicious); answering after a stall → timing is descriptive only; CORRECTION_PROTOCOL (preserve first value, record reason, reconfirm, downgrade certainty rather than fail); NDA refusal → offer an independent verification route without requiring disclosure.

Corpus organization: 10 legitimate (ambiguity, correction, stress, failed OOB); 10 obvious attacks; 10 sophisticated attacks with correct public facts; 10 malformed/adversarial interaction calls; mutation tests (transcript fragments, tool arrival order, timestamps); policy-property tests ("no path emits STAGE when required OOB evidence is absent"). Need an EVALUATION_INCOMPLETE → ESCALATE/NO_ACTION path.

## 4. Architecture attacks
The browser engine provides responsiveness and visualization and zero security authority; say that plainly. Malicious browser can modify the JS engine, suppress contradictions/pressure/transcript, forge UI states, alter timestamps, submit an edited log, invoke client tools, replay tokens, open many sessions, feed synthesized audio, race the UI against the server, send malformed values to hit fail-open paths, craft a two-failure path. The server cannot rerun facts it never independently observed.

Trust model: browser = mic, speaker, transient visualization, consent, untrusted; AssemblyAI session = event stream, authenticated transport, not authorization evidence by itself; server conversation gateway = canonical event recorder, sequence validator, challenge issuance and nonce tracking, evidence normalizer, the ONLY policy evaluator with authority, the ONLY tool-action gateway; mock systems = independently signed responses tied to session id, request id, challenge nonce, expiry; payment mock accepts only server-signed policy-approved commands. If the browser must connect directly for latency, treat browser copies as display-only and require a server-side signed event chain; if canonical events cannot be obtained server-side, say the demo is a client UX prototype, not a production trust architecture.

Tokens: one token binds to one session id, bound to origin, agent id, issued-at, expiry, max duration; consumed atomically; explicit reconnect rules; server enforces concurrency, daily quota, kill switch; never trust client-reported usage; abuse failure defaults to no new session. Verify the "AssemblyAI enforces the hard maximum" claim against the token API before the deck.

LLM-mediated answer tool is the biggest technical flaw: the LLM decides which utterance is an answer, which challenge, whether correct, whether to call, how to map. Substring validation proves only that words appeared somewhere. Close it: server issues challenge with cryptographic id and typed expected-answer set; server records the next eligible caller turn(s) under strict turn/time-window rules; deterministic normalization; server compares; if semantic interpretation is unavoidable the output is AMBIGUOUS, never PASS; LLM gets read-only goal "Ask challenge CH-17 exactly once, without revealing the expected answer"; policy receives only server-produced evidence with challenge_id, question_issued_at, eligible_turn_ids, raw_quote, normalization_result, match_result, confidence, source_hash. The LLM may ask. It may never grade.

Conference wifi table: mic preflight; AudioWorklet unlock gesture and Chrome/Edge requirement; worker degradation never affects server policy; 24 kHz ≈ 768 kbps mono; captive portals; barge-in event ordering (server interruption event canonical, fade locally, label pending); async checks time out with monotonic decisions, pending/timeout → ESCALATE never STAGE; resume speech context only and invalidate authorization evidence; health endpoint, warm-up monitor, static replay hosted independently; quota reserve and automatic replay failover.

Decision-table exploits: $50k threshold → structuring (need cumulative exposure by principal, beneficiary, purpose, rolling window); "zero failures → STAGE" unsafe (define affirmative assurance requirements, not absence of failures); pending-check DoS/confusion (bind checks to request_version; a material change invalidates prior successes; cap restart loops); failure counting gameable ("three independent failures" undefined); pressure-alone-no-op too broad (should change the operational path: preserved evidence, shorter disclosure, supervisor notification, no disclosure of sensitive details); no-response is not failure of identity (state UNVERIFIED, not IMPOSTOR); public policy means public challenge inventory (publish policy class and invariants, never active per-user challenge data or seeds); first-match ordering hides reasons (out-of-scope after a high-risk request must not erase it); no monotonic safety invariant (STAGE impossible without valid request version, verified identity assurance, successful current OOB, recognized beneficiary context, second-approval creation; material change invalidates dependent evidence; infrastructure failure → NO_ACTION/ESCALATE; LLM cannot create PASS/STAGE/FREEZE/action payloads). APort acknowledges composability/structuring as a limitation.

## 5. UX, voice, character
First five seconds: "cool voice-agent control-room dashboard," not "this prevents a social-engineering transfer." Too many metaphors at once: a mood board with a security thesis. Misreads: line-drawn face = avatar chatbot; dashed caller portrait = the system pre-judged the caller before evidence (undermines the behavioral-verification honesty); freeze = gimmick; waveform = generic voice UI; state machine = developer diagram; evidence stack = accumulating reasons to convict; failure tally = a fraud score (you reject voice inference but visually recreate it as a score); tool feed = debug console; two-role cheat sheet = the correct answers are written here; consumer coda = could not choose a customer.

First screen answers three questions: what is requested, what is still unverified, what happens if verification fails. Layout: TOP the request ($1,800,000 NEW ESCROW WIRE, REQUESTED BY "ROBERT MILLER"); CENTER conversation with the disputed claim highlighted; RIGHT three verification gates only (request context, verified device, claim consistency); BOTTOM "No funds can move by voice alone. Second approval required." Evidence ledger as drill-down after the call. Keynote: one cinematic claim-and-proof screen (large request, three live gates, strike-through $1.8M → $2.1M, device check awaiting → no confirmation, "No funds moved.", "Second approval was never created. Incident record sealed."), then the forensic screen. No face, no waveform, no state machine, no tool log, no 12 cards.

Character: a liability unless restrained; the dashed portrait is particularly bad, it telegraphs guilt before verification. Replace both portraits with roles and assurance states (CLAIMED: Robert Miller / VERIFIED CHANNEL: not established / REQUEST OWNER / APPROVER). If retained, tiny and functional. Cheat sheet: replace with two brief role prompts without answers (Dana: "request an earlier release of the scheduled Meridian Supply payment, your own wording"; unverified caller: "request a confidential escrow transfer, improvise"); hidden facts revealed only after the call. Replay mandatory, same event stream, same trace, same timing; label "Recorded adversarial replay" with play/pause/speed and the event log.

## 6. What would beat it
"Verity Line": a voice-native authorization layer for high-risk help-desk and treasury changes that converts a spoken request into a signed, policy-bound Authorization Packet downstream systems accept, reject, or route. Premise: "A phone call can request a privileged action. It cannot authorize one." Judge says any arbitrary request (e.g., "reset the production break-glass account, I'm at the airport"); the system builds a live packet (action, scope, claimed requester, reason, evidence with provenance, policy, outcome ESCALATE, no reset performed); the judge changes the request; the request version changes; old evidence is visibly invalidated. Would switch? Yes, partially: keep the name Countersign, the core sentence "voice can request, never release," evidence provenance, barge-in/containment; abandon the "deepfake-era identity governance" framing, the consumer coda, the portrait, browser-side policy theatrics, the fixed Hartwell interrogation as the main demo. Winning version: "Countersign: a voice-to-authorization-packet runtime for high-risk changes," treasury wire as one policy pack and privileged credential reset as a second.
